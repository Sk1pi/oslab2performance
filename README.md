# oslab2performance
# Lab 2. Performance Measurement and Analysis (+ Assembler and low-level optimisation)

Дослідження продуктивності, енергоспоживання та впливу оптимізацій компілятора на прикладі програми множення матриць на C.

## Середовище

| | |
|---|---|
| Ноутбук | ASUS TUF Gaming F17 (FX707ZC4) |
| Процесор | Intel Core i5-12500H (Alder Lake: 4 P-ядра + 8 E-ядер), підтримує SSE4.2, AVX, AVX2, FMA; AVX-512 не підтримується |
| ОС | Windows 11 + WSL2, Ubuntu (ядро 6.18.54.1-microsoft-standard-WSL2) |
| Компілятор | gcc 15.2.0 |
| Профайлер | perf 6.12.0 (зібраний із вихідного коду ядра з підтримкою libelf, бо системний perf у WSL не вмів читати символи функцій) |
| Енергія | HWiNFO64 8.55 (зчитує Intel RAPL з боку Windows) |

## Програма

`matmul.c` множить дві квадратні матриці `float` розміру N×N (за замовчуванням 1024, у всіх замірах N = 2048):

- `init_matrix` заповнює матриці випадковими числами через `rand()`;
- `multiply` виконує множення трьома вкладеними циклами (n³ ≈ 8,6·10⁹ операцій множення-додавання). Порядок циклів `i → k → j` обрано так, щоб внутрішній цикл ішов по пам'яті послідовно і компілятор міг його векторизувати;
- `checksum` рахує суму елементів результату, щоб компілятор не викинув обчислення як невикористані.

Дві версії:

```bash
gcc -O0 -g -fno-omit-frame-pointer matmul.c -o matmul_O0                 # без оптимізацій
gcc -O3 -march=native -g -fno-omit-frame-pointer matmul.c -o matmul_O3   # оптимізації + AVX2/FMA
```

`-g` і `-fno-omit-frame-pointer` потрібні, щоб perf бачив назви функцій і стек викликів.

Усі кроки можна повторити однією командою: `./run_all.sh` (енергію міряємо окремо, вручну).

## 1. FlameGraph

```bash
perf record -e cpu-clock -F 999 -g -o perf_O0.data ./matmul_O0 2048
perf script -i perf_O0.data > out_O0.perf
~/FlameGraph/stackcollapse-perf.pl out_O0.perf > out_O0.folded
~/FlameGraph/flamegraph.pl out_O0.folded > flame_O0.svg
```

1. `perf record` 999 разів на секунду фіксує, яка функція виконується, разом зі стеком викликів (`-g`).
2. `perf script` перетворює бінарні дані на текст.
3. `stackcollapse-perf.pl` згортає однакові стеки в один рядок із кількістю повторень.
4. `flamegraph.pl` малює інтерактивну SVG.

Результат: [`flame_O0.svg`](flame_O0.svg), [`flame_O3.svg`](flame_O3.svg).

**Інтерпретація (O0).** Ширина блоку — частка часу, вертикаль — стек викликів (знизу вгору: `_start` → `__libc_start_main` → `main` → `multiply`). Функція `multiply` займає майже всю ширину, тож це «гаряча точка» програми. `init_matrix` і `rand` ледь помітні зліва, а `checksum` взагалі не видно, бо вони мають складність n², а не n³.

## 2. Статистика виконання

### 2.1. `/usr/bin/time --verbose` ([`time_O0.txt`](time_O0.txt), [`time_O3.txt`](time_O3.txt))

| Показник | O0 | O3 |
|---|---|---|
| User time | 16,04 с | 0,93 с |
| System time | 0,05 с | 0,04 с |
| Elapsed | 16,09 с | 0,98 с |
| CPU | 99% | 99% |
| Max RSS | 50 932 КБ | 50 936 КБ |
| Minor page faults | 16 468 | 16 467 |
| Major page faults | 0 | 0 |
| Voluntary / involuntary context switches | 4 / 68 | 2 / 5 |

- Майже весь час припадає на user mode, а 99% CPU означає, що програма однопотокова і обмежена обчисленнями.
- Max RSS ≈ 50 МБ відповідає трьом матрицям: 3 × 2048² × 4 Б = 48 МБ, плюс код і бібліотеки.
- Minor page faults виникають під час першого звернення до кожної 4-КБ сторінки пам'яті; major = 0, бо нічого не читалося з диска.
- Примусові перемикання контексту (68) виникають, коли ОС забирає процесор після закінчення кванту часу.

|---|---|---|
| `multiply` | 99,77% | вбудована в `main` |

## 3. Енергоспоживання

RAPL у WSL недоступний ([`rapl_check.txt`](rapl_check.txt): `/sys/class/powercap` не існує), тому ті самі дані RAPL зчитувались з боку Windows програмою HWiNFO (датчик **CPU Package Power**). Перед кожним заміром середні значення скидались, і замір тривав рівно стільки, скільки працювала програма. Версія O3 запускалась 15 разів поспіль, щоб замір тривав достатньо довго для частоти оновлення HWiNFO.

| Замір | CPU Package Power (середнє) | Ядра IA | Час |
|---|---|---|---|
| Простій (фон) | 11,93 Вт | 6,59 Вт | — |
| O0, 1 запуск | 25,57 Вт | 20,38 Вт | 14,95 с |
| O3, 15 запусків | 21,43 Вт | 15,66 Вт | 13,09 с (0,873 с/запуск) |

- **3.1. Енергія системи** (E = P · t): O0 ≈ **382 Дж**, O3 ≈ **18,7 Дж** за запуск.
- **3.2. Енергія лише програми** (E = (P − P_idle) · t): O0 ≈ **204 Дж**, O3 ≈ **8,3 Дж** за запуск.

Скріншоти: `hwinfo_idle.png`, `hwinfo_O0.png`, `hwinfo_O3.png`. Детальні числа: [`energy.txt`](energy.txt).

Обмеження: міряється потужність процесора, а не всього ноутбука; «простій» включає фонові процеси Windows, але він однаковий для обох версій, тому порівняння коректне.

## 4. До і після оптимізації

### 4.1. Асемблер ([`matmul_O0.s`](matmul_O0.s), [`matmul_O3.s`](matmul_O3.s), [`annotate_O0.txt`](annotate_O0.txt), [`annotate_O3.txt`](annotate_O3.txt))

```bash
gcc -O0 -S -masm=intel matmul.c -o matmul_O0.s
gcc -O3 -march=native -S -masm=intel matmul.c -o matmul_O3.s
perf annotate -i perf_O0.data --stdio -M intel multiply
```

**O0**: внутрішній цикл має ~40 інструкцій на одне множення-додавання. Фрагмент:

```asm
mov    eax,DWORD PTR [rbp-0x10]   ; i читається зі стеку
imul   eax,DWORD PTR [rbp-0x2c]   ; i*n
add    eax,edx                    ; + j
cdqe                              ; int -> 64 біти
lea    rdx,[rax*4+0x0]            ; * sizeof(float)
...
movss  xmm0,DWORD PTR [rax]       ; одне число b[k][j]
mulss  xmm0,DWORD PTR [rbp-0x4]   ; * a[i][k]
addss  xmm0,xmm1                  ; + c[i][j]
movss  DWORD PTR [rax],xmm0       ; записати c[i][j]
add    DWORD PTR [rbp-0x8],0x1    ; j++ прямо в пам'яті
```

Усі змінні зберігаються в стеку і перечитуються на кожній ітерації, адреси перераховуються тричі, обчислення скалярні (`ss` = scalar single, одне число за раз).

**O3**: внутрішній цикл має 6 інструкцій:

```asm
vmovups      ymm0, [r8+rax]          ; 8 чисел b[k][j..j+7]
vfmadd213ps  ymm0, ymm2, [r15+rax]   ; ymm0 = ymm0*a[i][k] + c[i][j..j+7]
vfmadd231ps  ymm0, ymm1, [rdx+rax]   ; ymm0 += a[i][k+1] * b[k+1][j..j+7]
vmovups      [r15+rax], ymm0         ; записати 8 результатів
add          rax, 0x20               ; +32 байти = 8 float
jne          ...
```

Зміни: векторизація (8 чисел за інструкцію), FMA, розгортання циклу по `k` (два рядки `b` за ітерацію), змінні в регістрах, лічильник без `cmp`. Разом: 16 множень-додавань за 6 інструкцій проти 1 за ~40.

### 4.1.1. AVX / SIMD

- `ymm` — 256-бітні регістри AVX, вміщують 8 чисел `float`; `ps` = packed single (операція над усіма 8).
- `vbroadcastss` копіює одне число `a[i][k]` в усі 8 позицій регістра.
- `vfmadd...ps` (FMA3) виконує множення і додавання однією інструкцією з одним округленням. Через це checksum O3 відрізняється в останніх цифрах (`...041.736` проти `...041.710`): інший порядок і кількість округлень у `float`.
- `grep -c ymm matmul_O0.s` = 0: у O0 немає жодної векторної інструкції.
- Інструкції з `xmm` (4 числа) і `vfmadd...ss` (1 число) в O3 обробляють «хвіст» циклу, коли N не ділиться на 8.
- AVX-512 (`zmm`, 16 чисел) процесор не підтримує, тому `-march=native` обрав AVX2.

### 4.2. Час та інші показники

| Показник | O0 | O3 | Різниця |
|---|---|---|---|
| Elapsed (`time`) | 16,09 с | 0,98 с | ~16× |
| task-clock (`perf stat`) | 15 894 мс | 1 073 мс | ~15× |
| Max RSS | 50,9 МБ | 50,9 МБ | однаково |
| Page faults | 16 468 | 16 467 | однаково |
| Context switches | 58 | 2 | менше, бо програма коротша |

Оптимізація змінила спосіб обчислення, але не обсяг даних, тому пам'ять і page faults не змінились.

### 4.3. FlameGraph після оптимізації

- `multiply` зникла з графіка: її код вбудований у `main`.
- Праворуч з'явилась помітна «вежа» `init_matrix → rand → random → random_r`. Її абсолютний час не змінився (~0,03–0,04 с), бо `rand` живе в уже скомпільованій libc і `-O3` на неї не впливає. Проте частка зросла з ~0,2% до ~2,3%, бо множення прискорилось у ~16 разів.
- Обидва графіки мають однакову ширину, хоча вибірок ~19 000 проти ~1 300: FlameGraph показує частки, а не абсолютний час.

### 4.4. Енергія після оптимізації

| | O0 | O3 | Різниця |
|---|---|---|---|
| Час запуску | 14,95 с | 0,873 с | ~17× |
| Середня потужність | 25,57 Вт | 21,43 Вт | нижча |
| Енергія системи | 382 Дж | 18,7 Дж | ~20× |
| Енергія програми | 204 Дж | 8,3 Дж | ~25× |

Основна економія з'являється через скорочення часу: E = P · t. Енергія зменшилась навіть сильніше за час, бо середня потужність O3 нижча: O0 виконує значно більше інструкцій (постійні звернення до стеку), а у серії запусків O3 є короткі менш навантажені фази (старт процесу, виділення пам'яті, `rand`).

## Висновки

- «Гаряча точка» програми — потрійний цикл множення (≈99,8% часу).
- `-O3 -march=native` прискорює програму в ~15–17 разів за рахунок регістрів замість стеку, векторизації AVX2 (8 `float` за інструкцію), FMA, розгортання циклу та inline-вбудовування функцій.
- Енергія на один запуск зменшилась у ~20 разів: швидша програма витрачає менше енергії.
- Обмеження WSL2: немає апаратних лічильників perf і RAPL, тому енергію довелося міряти з боку Windows.
